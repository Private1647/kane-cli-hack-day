# Test environment for the designed kane-cli suite

Status: decision by the organiser, 2026-10-23. This note is about where and how the designed browser tests run. It adds no product feature and no new use-case.

## Base URL

- Every designed test runs against the local app at **http://localhost:3100**. Every navigation step starts there, for example `http://localhost:3100/live`, `http://localhost:3100/match`, `http://localhost:3100/activate`, `http://localhost:3100/studio/{slug}/deck`.
- `kaneclihack.sh` (and `https://kaneclihack.sh/...`) is the **production** domain named in the product specification. It is never a test target: a test that opens it writes test data into the live event database. A route the specification writes as `kaneclihack.sh/<path>` is tested as `http://localhost:3100/<path>`.
- Steps say "Go to http://localhost:3100/<path>". The test never starts from a blank tab, a search engine, or browser history.

## What a step can ask the browser agent to do

The test agent drives one Chrome tab, like a person with a mouse and keyboard. It cannot open DevTools panels to block, throttle or interrupt a network request, restart Chrome, decode a QR image, or scan with a camera. Steps ask for user actions and visible outcomes.

It can also make a direct HTTP request itself ("Call POST http://localhost:3100/api/v1/kane/runs with header Authorization: {{kane_adapter_credential}} and body …, save the response as run") and assert on the response status and body. Such a call carries only the credential the step passes explicitly, such as a bearer token. It never carries the browser's sign-in cookie, so an endpoint that needs the signed-in browser session is exercised through the page, not by a direct call. The Kane result-adapter API (`/api/v1/kane/runs`) takes a bearer token, so those tests call it directly at http://localhost:3100 and then check the result on the team's pages.

- **Badge QR codes.** The badge QR (on the passport card front and on the printable badge at `/passport/badge`) is an image with no link text. A step never decodes it. The printable badge shows the Offline ID P-code next to the QR, which a step can read. A step that needs the public badge page (`/passport/b/{token}`) opens it from a fixture variable that holds that participant's current badge URL, and a step that checks rotation keeps that pre-rotation URL. "Lost my badge: rotate QR" opens a confirmation that must be confirmed.
- **Live stream outage on `/live`.** A step never interrupts the stream in DevTools. An organizer stages the outage in the app: at `/ops/integrations`, "Pause · mark status…" on "Live TV stream" (Pause, or Mark status Down, with a reason). `/live` then shows a "Live stream" alert and holds the last values instead of resetting them to 0. Resuming the system, or marking it OK, ends the outage.
- **Two people in one test.** There is one browser session at a time. To act as a second person, the step uses "Sign out" and then signs in as that person. Staff one-time codes are single use, so a test never signs out a staff session it still needs, and never asks for two staff sessions to be open together. A competing claim is tested in order: the first mentor claims the ticket and signs out, then the second mentor signs in and tries to claim the same ticket, and the step checks that the second claim is refused or that no Claim is offered because the ticket is already claimed.
- **Sign-in routes.** Team hub: `/login` with team name and team password. Personal (passport, finalizing a submission): `/passport/login` with email and password; a step names the password and never switches to "Use a one-time code instead" unless the test supplies a code. Signing in personally also opens that participant's own team hub, so a test that only knows a participant's email and password signs in at `/passport/login`, never at the team-password gate. Staff (organizer, mentor, judge): `/ops/login` with staff email and one-time code. Finalizing a submission is a personal step: the captain signs in at `/passport/login` with the captain email and personal password.
- **The first step carries the credentials.** A test's first step names the sign-in page and the credentials together, for example "Go to http://localhost:3100/passport/login and sign in with {{participant_email}} and {{participant_password}}". A step never says only "go to the sign-in page" or "sign in": without the values in the step the agent improvises (it guesses, or picks the one-time code option) and the test fails before it reaches the behaviour under test.
- **Switching from staff to a participant.** A staff session and a participant session do not mix in one browser. A test that acts as an organizer, mentor or judge and then as a participant (or the reverse) clicks "Sign out" first (the staff area's "Sign out" is in its top bar), then signs in as the participant at `/passport/login` with that participant's email and password.
- **Variables.** A step uses only the plain `{{name}}` variables the suite declares in `.testmuai/variables/assurance.json`. It never uses the `{{global.*}}` form, which reads Test Manager instead of the local file and is never filled. A value the test produces during the run (a receipt code, a deck version) is stored with "store … as" and referred to in words afterwards, not as a new `{{variable}}`.
- **Server behaviour** (a deadline refusal, a retry that must not create a second receipt) on an endpoint that needs the signed-in browser session (finalizing a submission, for example) is checked from what the page shows after the user action: the message, the receipt code, the receipt list. Not from a raw API response.

## Tests that play a human role

- **Judge.** The automation acts as the judge account, and the judge's decision is the input the test states. A step gives the anchor value for each category, then commits. The checks are that the score form starts with no AI-suggested or pre-filled final score, and that the committed score shows exactly the values entered by the judge account. A test does not claim the judge "decided alone" while the automation picks the scores.
- **Idea Validator.** The validator lists all eight checklist topics (functional deliverable, agent use, Kane integration, repeatability, feedback, actual proof, engineering impact, feasible demo) and marks each one met, partial or missing, with a quote from the idea or "Not mentioned" as its evidence, and a summary such as "3 of 8 criteria are clearly covered". An idea written to be weak or incomplete is expected to have some topics "Not mentioned" and a verdict of needs_work or ineligible. "Considers every topic" means every topic is listed with a status, not that every topic passes. A test that expects every topic to be covered writes an idea that mentions every topic.

## How a step identifies people and records

- **People in matching and introductions.** The app deliberately never shows a participant's email or phone in match suggestions or introductions; it shows the display name. A step that finds or checks a person on `/match` (a suggestion, a pending introduction "from" someone, an accepted introduction) identifies them by display name: `{{participant_display_name}}` for the participant and `{{other_participant_display_name}}` for the other participant. The email is used only to sign in, and the privacy check is that the email is absent.
- **Finalizing twice.** A retried finalize must not create a second receipt. The team's Submit page (`/t/{slug}/submit`) shows the team's one receipt code; it has no team-wide receipt count. The test stores the receipt code shown after the first finalize, retries (a second click of Finalize, or reloading the finalized page), and checks the Submit page still shows that same single receipt code and no second one.
- **A full team.** Joining a team needs an invite code. The test that tries to add a fifth member to the full four-person team `{{full_team_slug}}` signs in as a teamless participant and enters the valid invite code `{{full_team_invite_code}}` for that team; the expected outcome is a refusal because the team is full, not a missing-code error.
- **Paper check-in ledger.** Paper check-ins go back in through the organizer's recovery page (`/ops/recovery`, "Batch upload paper ledgers", the check-in ledger). The step says "upload the file at {{offline_checkin_ledger}}"; the variable holds the path of the CSV on this machine. It never asks the agent to type or invent ledger rows.
- **Badge rotation.** The rotation test first goes to the stored pre-rotation badge URL `{{participant_badge_url}}` (the full `http://localhost:3100/passport/b/<token>` address) and checks the public badge shows, then rotates on `/passport` ("Lost my badge: rotate QR", confirm "Yes, rotate QR"), then navigates to that same full URL again and checks the revoked-badge alert.
- **Privileged recovery.** An organizer inspects a finalized team's submission receipt from the submissions list at `/ops/submissions` (open the team's row, then its receipt), not from `/ops/recovery`, which holds the paper ledgers and manual receipts.

## Not run unattended

- The selfie step needs a person to press the camera shutter; Kane never takes the selfie. A test that ends in a captured selfie is run attended only. Other activation tests stop before the shutter (camera denied and skipped, or the pending Selfie step).
- Photo upload, evidence files and screenshots are stored in Vercel Blob, which is not configured on the local machine. A test that uploads a photo or an evidence file is expected to fail locally at the upload; that is the environment, not the app.
